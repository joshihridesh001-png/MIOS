## 1. Repository Structure

### Current Problem
The Next.js application lives inside a nested `app/` folder.  
The repository root contains documentation and the `app/` directory, which itself contains `package.json`, `src/`, and all application code.

This is non-standard and makes the project harder to understand, clone, and work with.

### Required Change
Choose one of the two options below and implement it cleanly:

**Option A (Preferred):**  
Move the entire Next.js project to the repository root.  
- `package.json`, `src/`, `next.config.ts`, etc. should live at the root.  
- Documentation can stay in a `/docs` folder.  
- Update all paths, import aliases, and deployment settings accordingly.

**Option B:**  
Keep the nested structure but make it intentional and clearly documented.  
- Add a root-level README that explains the structure.  
- Ensure tooling, scripts, and Vercel configuration work correctly with the nested layout.  
- Avoid leaving the structure looking accidental.

### Acceptance
- [ ] Repository structure is either moved to root or clearly documented as intentional
- [ ] `npm install` and `npm run dev` work from the correct directory without confusion
- [ ] Vercel deployment continues to work
- [ ] Documentation reflects the final structure

## 2. Experiments – Purpose

The Experiments section must answer this primary question:

> Did this creative, offer, style, or branding perform better or worse than our current best on CTR, CVR, CAC, and related metrics?

It must also:
- Act as a permanent library of all tests
- Help maximize accurate learning per rupee of ad spend
- Make extraction of high-quality Learnings easy
- Feed the Knowledge Base with correctly scored knowledge

---

## 3. Locked Product Decisions

| Topic | Decision |
|-------|----------|
| Relationship to Campaigns | Keep separate. Allow a Campaign to be flagged as experimental. Strong linking is required. |
| Confidence on new Learning | Recalculate using the full weighted formula (Sample 30% + Consistency 25% + Effect Size 20% + Recency 15% – Contradiction Penalty). Do not inherit the experiment confidence number unchanged. |
| Conflict with previous results | Latest result is strongly weighted. System must flag low sample size, possible skew, or contradiction with existing high-confidence learnings. Human confirmation is required before the new result becomes institutional truth. |
| Statistical depth this cycle | Practical sample-size suggestions and early-winner prevention only. Full power analysis and audience simulation are deferred. |
| Optimization goal | Accurate learning per unit of ad spend. |

## 4. Experiments User Flow

### 4.1 Plan Experiment

Required fields:
- Name
- Hypothesis
- Primary metric (CTR, CVR, CAC, or custom)
- Control (linked creative or offer)
- Variant A (linked)
- Variant B (optional)
- Linked Campaign(s)
- Target audience or notes
- Minimum lift that matters (default 15%)
- Desired confidence level (default 80%)

System must:
- Calculate and show suggested sample size per variant
- Show rough budget estimate when baseline CPM/CPC data exists
- Prevent saving without Control + at least one Variant

### 4.2 Record Results

Supported input:
- Manual entry
- Existing Quick-Paste parser (improve where possible)

Metrics to capture for Control, Variant A, and Variant B:
- Spend
- Impressions
- Clicks
- CTR (calculated)
- Conversions / Leads
- CVR (calculated)
- Customers
- Revenue
- CAC (calculated)
- CPM (calculated)
- ROI (calculated)

System must:
- Calculate lift versus Control on the primary metric
- Compare each variant against the current best performing creatives on the same metric
- Show a clear winner or “no clear winner”
- Warn or block when sample size is below the suggested threshold

### 4.3 Analysis View

Must be visible without excessive scrolling:
- Side-by-side comparison (Control vs Variants vs Current Best)
- Lift percentages
- Absolute differences on CAC and ROI
- Plain-language insight generated by the system
- Sample size status (sufficient / insufficient)
- Flags for possible skew or low confidence

### 4.4 Learning Extraction

When the user marks the experiment complete or clicks “Create Learning”:

1. System creates a draft Learning containing:
   - Concise insight statement
   - Key metrics and lifts
   - What worked
   - What failed
   - Recommended next action
2. User can edit the draft
3. System asks: “What did we learn from this?”
4. On confirmation:
   - Learning is saved
   - Confidence is recalculated with the full institutional formula
   - Learning is tagged (Creative, Offer, Emotion, Audience, Platform, etc.)
   - Entry is added to the Knowledge Base
   - Experiment status is set to Completed

### 4.5 Library / List View

Must support:
- Filter by status (Queued, Running, Completed, Aborted)
- Filter by primary metric, platform, date range
- Search by name or hypothesis
- Sort by date, confidence, lift, or spend
- Visual indication of winner and whether sample size was sufficient

## 5. Sample Size Guidance

Show a suggested minimum sample size per variant based on:
- Current baseline of the primary metric
- Minimum lift the user cares about
- Target confidence level

Reference thresholds (can be adjusted later):

| Focus                        | Minimum per variant              |
|------------------------------|----------------------------------|
| CTR differences              | 1,000 – 2,000 impressions        |
| CVR / Lead differences       | 40 – 80 conversions              |
| CAC / Customer differences   | 50 – 100 customers               |
| Decision to scale            | Higher bar + multi-day consistency |

Behavior:
- Show suggestion at planning time
- Re-check when results are entered
- Show persistent warning if user tries to declare a winner below threshold
- Allow override only with explicit acknowledgment

## 7. Data and Linking Rules

- Every experiment must support links to one or more Creatives
- Every experiment must support links to one or more Campaigns
- A Campaign can be marked “Experimental” without appearing in the Experiments list
- Deleting a Creative or Campaign must not delete historical experiment records (use soft references or snapshots)

---

## 8. Contradiction Handling

When a new completed experiment conflicts with existing high-confidence Learnings:
- Surface the conflict clearly
- Show sample size and key metrics for both the new result and the previous learning
- Require explicit confirmation before institutional knowledge is updated
- Log the decision for audit

---

## 9. Forgot Password and Security

Implement full password recovery using Supabase Auth:

- “Forgot password?” link on the login page
- Page to request a reset (email input)
- Supabase recovery email flow
- Reset password page that accepts the recovery token
- Clear success and error states
- Basic protection against abuse
- Remove any hardcoded credential examples from the UI and documentation

Additional security hygiene:
- Review session and cookie settings
- Ensure no production credentials or demo accounts are exposed in client code or public docs

---

## 10. Demo Mode Foundation

Structural requirements only (full public demo is not required yet):

- Support a clear mode flag: `production` or `demo`
- Demo mode must use completely isolated data (separate seed data or separate schema/project)
- Show a visible indicator when the user is in Demo mode
- Provide an entry path that places a user into Demo mode without access to real Eradicant data
- Guarantee that production queries never return demo data and vice versa
